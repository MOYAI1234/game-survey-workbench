# 游戏问卷研究工作台设计文档

**日期：** 2026-03-12

**目标：** 构建一个面向游戏行业、由个人研究者使用的本地优先工具，用知识库驱动问卷设计、问卷结果分析和 Markdown 报告生成。

## 1. 背景与目标

这是一个全新的系统，不复用现有业务架构，也不以多人协作为目标。系统的主要使用者是研究者本人，因此优先级是：

- 放大研究能力，而不是做团队平台
- 提高分析质量和一致性，而不是追求复杂流程编排
- 让设计问卷、分析数据、撰写报告三件事共享上下文，但可以分别独立进行

系统需要覆盖三类核心能力：

- 基于知识库生成和优化问卷文档
- 导入回收表格后，结合知识库做分析
- 生成可继续人工修改的 Markdown 报告

## 2. 产品定位

推荐把产品定位为“知识库驱动的游戏问卷研究工作台”，而不是固定流水线。

不采用强串联流程的原因：

- 问卷设计完成后，往往会经历多轮修改
- 数据回收和分析通常与设计阶段存在时间间隔
- 同一项目可能在不同时间用不同口径重复分析

因此系统应提供三个独立入口：

- 问卷设计
- 数据分析
- 报告生成

这三个入口共享同一个项目上下文、知识库选择、问卷定义和历史运行记录。

## 3. 目标用户与使用场景

### 目标用户

- 个人使用的游戏行业研究者/分析师

### 典型场景

- 围绕某个研究主题建立项目，例如新手引导体验、版本满意度、活动反馈、付费体验
- 基于研究目标和理论知识库设计问卷草案
- 隔一段时间后导入回收表格做结构化分析与开放文本分析
- 输出 Markdown 报告，继续人工润色或进入后续汇报流程

## 4. 输入与输出

### 输入

#### 知识库输入

- 统一使用 Markdown 作为知识库原始格式
- 即使原始资料来自 PDF、Word 或网页，也先转换为 Markdown 再导入

#### 问卷数据输入

支持以下常见题型：

- 单选
- 多选
- 量表题
- 矩阵题
- 开放题
- 单选/多选中的“其他，请说明”类开放补充

### 输出

- 问卷设计文档
- 分析运行结果
- Markdown 报告

## 5. 方案对比与选择

### 方案 A：单体工作台

一个本地应用内提供知识库管理、问卷设计、数据分析和报告生成。

优点：

- 架构简单
- 易于迭代
- 适合个人工具

缺点：

- 未来若扩展为平台，模块拆分成本较高

### 方案 B：工作流编排型系统

所有流程都通过任务节点串联，例如导入知识库、生成问卷、导入数据、生成报告。

优点：

- 流程清晰
- 易于复跑和自动化

缺点：

- 过于强调线性流程，不符合当前使用习惯

### 方案 C：文档中心型助手

围绕 Markdown 文档组织设计、分析和报告。

优点：

- 文档质量高
- 可编辑性好

缺点：

- 结构化分析能力容易偏弱

### 最终选择

采用“方案 A + 方案 C”的组合：

- 外层是本地研究工作台
- 内部产物和输出以 Markdown 为核心

这样既能保留数据分析能力，也能保证文档可控性和可追溯性。

## 6. 整体架构

系统建议拆成五层：

### 6.1 知识库层

负责接收、切片、索引和检索 Markdown 知识文档。

### 6.2 问卷设计层

根据研究目标和知识库生成题目草案、维度建议、题型建议，并支持多轮优化。

### 6.3 数据理解层

读取问卷回收表，识别题型结构、题目映射、矩阵结构和“其他文本”等混合输入。

### 6.4 分析引擎层

组合确定性统计和 LLM 驱动的洞察分析：

- 统计部分负责稳定、可验证的计算
- 模型部分负责文本归纳、洞察解释和结合知识库的结论生成

### 6.5 报告生成层

将问卷定义、分析结果和知识库依据汇总为 Markdown 报告。

## 7. 核心设计原则

- 问卷设计、数据分析、报告生成必须独立可用
- 三个模块共享项目上下文，但不强制串联
- 知识库不只是用于检索，还要参与设计标准、分析框架和报告解释
- 每次关键产物都保留版本，便于隔天继续工作
- 所有最终输出都尽量附带知识依据和数据依据

## 8. 核心对象模型

系统建议以 `Project` 作为主对象，而不是以单次任务作为主对象。

### 8.1 Project

表示一个具体研究主题。

### 8.2 Knowledge Pack

从总知识库中为当前项目选出的知识子集。目的是避免每次都在全量知识中检索，降低噪声。

### 8.3 Questionnaire Spec

记录问卷设计真相源，包括：

- 研究目标
- 研究假设
- 维度设计
- 题目内容
- 题型
- 选项
- 跳题逻辑
- 每题的分析意图

### 8.4 Survey Dataset

保存原始回收表和清洗后的标准化数据。

### 8.5 Analysis Run

表示一次分析执行结果，用于记录：

- 使用的数据版本
- 使用的知识包
- 使用的分析配置
- 生成的中间结论和结果文件

### 8.6 Report

最终 Markdown 报告及其关联资源。

## 9. 文件组织建议

```text
workspace/
  knowledge/
    theory/
    game-research/
    analysis-frameworks/
  projects/
    project-a/
      project.md
      questionnaire/
        spec.md
        versions/
      data/
        raw/
        cleaned/
        schema/
      analysis/
        run-2026-03-12/
      reports/
        report-2026-03-12.md
      assets/
```

关键原则：

- 总知识库长期积累
- 每个项目只绑定相关知识
- 问卷定义、数据、分析结果、报告彼此独立存档
- 同一项目允许多次分析运行

## 10. 知识库设计

### 10.1 知识库分层

知识库建议拆为三层，而不是简单堆进一个向量库：

#### 理论层

- 问卷设计原则
- 用户研究方法
- 量表设计与解释原则
- 开放题编码与文本分析方法

#### 行业层

- 游戏行业研究框架
- 品类差异
- 玩家分层
- 版本体验分析框架
- 活动反馈分析框架
- 付费与留存相关分析框架

#### 经验层

- 个人历史项目经验
- 常见报告表达方式
- 已验证有效的分析口径
- 常用结论模板与判断规则

### 10.2 知识条目元数据

每篇知识文档建议补充元信息：

- 文档类型：理论 / 行业 / 经验
- 适用场景：新手引导 / 活动 / 版本 / 付费 / 留存等
- 适用阶段：问卷设计 / 数据分析 / 报告生成
- 优先级或可信度
- 关键词

### 10.3 知识库与系统的连接方式

系统不应让用户每次手动搜知识，而应通过 `Knowledge Pack + 检索策略` 自动注入知识。

推荐规则：

- 问卷设计时优先调用理论层 + 行业层
- 数据分析时优先调用行业层 + 经验层
- 报告生成时同时调用分析结果和相关理论/经验依据

### 10.4 知识库闭环

知识库需要支持双向流动：

- 正向：知识库指导问卷设计、分析和报告
- 反向：优质问卷、优质报告、成熟结论沉淀回经验层

## 11. 三个核心模块的工作流

### 11.1 问卷设计模块

输入：

- 研究目标
- 目标人群
- 业务背景
- 待验证假设
- 当前项目使用的 Knowledge Pack

输出：

- 研究维度建议
- 每个维度的题型建议
- 题目与选项草案
- 量表和开放题补充建议
- 设计风险提示

该模块应支持多轮优化，重点是提高研究质量和可分析性，而不是一次性生成最终问卷。

### 11.2 数据分析模块

首先进行标准化理解：

- 识别列与题目的映射关系
- 识别题型
- 识别量表范围
- 识别矩阵结构
- 拆分“其他文本”等混合字段

然后拆为两类分析：

#### 确定性分析

- 样本量
- 频数与占比
- 均值与分布
- Top/Bottom box
- 多选题分布
- 交叉分析
- 矩阵拆解

#### 知识库增强分析

- 结合行业框架解释结果
- 识别玩家动机和体验问题
- 解释满意度、阻力、留存风险等可能原因

开放题及“其他文本”建议走单独文本分析链路：

- 去噪
- 主题归并
- 倾向判断
- 与量化结果交叉解释

### 11.3 报告生成模块

建议输出结构：

- 研究背景与目的
- 样本说明
- 核心发现
- 分维度分析
- 关键人群/关键题目拆解
- 开放反馈总结
- 结论与建议动作
- 附录：题目、统计口径、引用依据

报告内容需要同时基于两类证据：

- 数据证据
- 知识证据

## 12. AI 与规则的职责边界

### 规则/代码负责

- 题型识别
- 数据清洗
- 统计计算
- 交叉分析
- 矩阵展开
- 文件与版本管理

### LLM 负责

- 问卷题目草拟
- 开放题归纳
- 洞察解释
- 报告撰写
- 基于知识库的研究建议

### 设计原则

应当由规则约束 LLM。模型输出应建立在明确输入上，包括：

- 问卷定义
- 统计结果
- 检索到的知识片段
- 指定的报告结构

避免模型在缺少依据时自由发挥。

## 13. 推荐技术架构

第一版建议使用本地优先的单体应用架构。

### 前端

- 轻量本地 Web UI
- 负责项目管理、知识库上传、问卷定义查看/编辑、数据导入、报告导出

### 后端

- 负责项目管理、知识库索引、任务执行、分析编排、报告生成

### 数据存储

- 数据库：项目、问卷定义、分析运行、知识元数据、报告版本
- 文件目录：Markdown 原文、原始表格、清洗结果、报告产物

### 检索层

- 对知识库切片
- 做 embedding
- 结合元数据过滤
- 为不同任务类型提供检索策略

### 模型调用层

- 封装提示词模板
- 管理上下文拼装
- 记录引用来源
- 支持缓存与复跑

### 推荐技术方向

若以快速落地为优先，推荐 Python 技术栈：

- FastAPI
- SQLite 作为第一版数据库
- 本地文件系统管理产物
- Python 数据分析生态处理表格和统计
- 向量索引或轻量检索组件处理知识库

## 14. MVP 范围

第一版建议只做以下六项能力：

1. 知识库导入
2. 项目创建与 Knowledge Pack 绑定
3. 问卷设计助手
4. 问卷结果导入
5. 分析运行
6. Markdown 报告生成

## 15. 暂不纳入第一版的内容

- 多人协作和权限系统
- 复杂流程编排器
- 高级可视化 BI
- 外部问卷平台深度集成
- 自动分群建模和因果推断
- 跨项目基准数据库
- 自动生成最终发放端问卷产品

## 16. 成功标准

第一版成功的衡量标准不是功能数量，而是以下问题是否被解决：

- 能否稳定利用知识库辅助问卷设计
- 能否可靠解析常见游戏问卷题型
- 能否在结构化统计基础上生成有方法论支撑的洞察
- 能否产出可直接继续编辑的 Markdown 报告
- 能否让不同时间点的问卷设计、分析和报告工作共享上下文

## 17. 后续推进建议

后续应进入实现规划阶段，产出一个面向零上下文执行者的详细实施计划，按小步、可测试、可提交的方式拆解。
