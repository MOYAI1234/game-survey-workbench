# 游戏问卷研究工作台数据质量增强设计文档

**日期：** 2026-03-12

**目标：** 在现有 MVP 基础上，优先提升真实问卷数据的理解准确率和分析输入质量，让“上传真实文件 -> 生成可信 schema -> 进入分析与报告”这条链路更稳定。

## 1. 背景

当前系统已经完成最小链路验证：

- 可创建项目
- 可上传真实 Excel/CSV
- 可生成 `analysis_run_id`
- 可生成 Markdown 报告

但真实数据验收暴露出核心短板不在“能不能跑”，而在“识别得准不准”：

- 多选题被识别成单选题
- 开放题被识别成单选题
- `标记`、`时间戳记` 等系统列被误当成分析题目
- 报告虽然可生成，但底层 schema 质量不足，后续统计与结论可信度受限

因此下一轮不再优先补大而全功能，而是聚焦数据理解层。

## 2. 本轮范围

本轮只做“数据理解与分析输入质量提升”，不做大规模产品扩展。

### 2.1 纳入本轮的内容

- 元数据列识别与过滤
- 题型识别规则增强
- 更稳定的标准化 schema 结构
- 将 `Analysis Run` 从临时 ID 提升为真实对象
- 为后续统计与报告消费提供更可靠的分析输入

### 2.2 暂不纳入本轮的内容

- 更复杂的前端交互设计
- 真正的可视化分析页面
- 完整 LLM 报告写作增强
- 跨项目知识闭环沉淀
- 外部问卷平台对接

## 3. 设计目标

本轮完成后，系统应满足以下目标：

1. 上传真实问卷文件后，系统可以明确区分“题目列”和“系统元数据列”
2. 对常见真实题型的识别明显优于当前 MVP：
   - 单选
   - 多选
   - 量表
   - 开放题
   - “其他，请说明”补充文本
3. 数据导入输出的 schema 能作为稳定的分析输入，而不是临时调试产物
4. `Analysis Run` 成为真实持久化对象，后续报告必须依赖其结果

## 4. 方案对比

### 方案 A：继续在现有 `question_columns` 上堆更多条件分支

优点：

- 改动最小
- 短期见效快

缺点：

- 规则会迅速变得难维护
- 很难清晰表达“这是元数据列还是题目列”
- 后续扩展矩阵题、交叉分析时容易失控

### 方案 B：引入“列分类 + 题型识别”两阶段结构

先判断一列属于哪一类，再对题目列做题型识别。

优点：

- 更接近真实数据处理流程
- 元数据列过滤会更清晰
- 更适合后续增加矩阵、分群、开放题链路

缺点：

- 比简单加条件分支多一层结构

### 方案 C：直接做完整数据字典与手工映射界面

优点：

- 精度最高
- 更贴近最终生产可用形态

缺点：

- 超出当前阶段
- 需要额外 UI 和人工配置流程

### 最终选择

采用 **方案 B**。

也就是：

- 第一步做列分类
- 第二步对题目列做题型识别
- 第三步生成标准化 schema
- 第四步基于 schema 创建真实 `Analysis Run`

这样既能显著提高准确率，又不会把当前项目过早做成复杂配置系统。

## 5. 核心设计

## 5.1 列分类层

新增列分类概念，把每一列先分为以下几类之一：

- `metadata`
- `question`
- `other_text`
- `unknown`

典型规则：

- `标记`、`时间戳记`、提交时间、设备信息等优先归为 `metadata`
- 名称中包含 `其他` / `other` 且与某主问题列强关联的归为 `other_text`
- 其他候选题目列归为 `question`

这个阶段的目标不是最终题型，而是先把“是否应该进入分析”判断清楚。

## 5.2 题型识别层

只对 `question` 类列继续识别题型。

建议支持的最小题型枚举：

- `single_choice`
- `multi_select`
- `scale`
- `free_text`
- `matrix`（本轮可先留接口，最低限度识别）

识别依据组合：

- 列名/题干关键词
  - 如 `Multiple Choices`
  - `please check`
  - `feel free`
  - `suggestion`
- 单元格内容分布
  - 数值型密度
  - 文本长度
  - 分隔符模式
  - 选项重复度
- 与 `other_text` 列的关联关系

原则是：

- 先靠稳定规则，不依赖模型
- 规则结果要可测试、可解释

## 5.3 标准化 Schema

当前 `question_columns` 结构过于扁平，不利于后续扩展。

建议演进成更明确的 schema 结构，至少包含：

- 列名
- 列分类
- 题型
- 是否纳入分析
- 关联的 `other_text` 列
- 识别依据摘要

这样后续即使人工验收发现问题，也能看到“为什么被识别成这样”。

## 5.4 Analysis Run 真实化

当前 `analysis_run_id` 只是导入时顺手生成的 UUID，语义不够完整。

本轮应引入真实 `Analysis Run` 对象，至少记录：

- `analysis_run_id`
- 关联项目
- 关联数据集
- 使用的 schema 版本
- 导入时间
- 是否完成基础标准化

后续报告生成必须引用该对象，而不是只靠字符串校验。

## 5.5 报告与分析的边界

本轮不追求报告内容大升级，但要收紧依赖关系：

- 报告只能基于已存在的 `Analysis Run`
- 报告读取的输入必须来自已持久化的 schema/分析结果
- 不允许报告逻辑绕过分析层直接从原始文件猜测结构

## 6. 数据流

目标数据流如下：

1. 用户上传 CSV/Excel
2. 系统保存原始文件
3. 系统读取表格并生成原始列画像
4. 系统执行列分类
5. 系统对题目列执行题型识别
6. 系统生成标准化 schema 并保存
7. 系统创建 `Analysis Run`
8. 后续统计、洞察、报告都消费该 `Analysis Run`

## 7. 测试策略

这一轮必须围绕真实样本暴露的问题补测试，而不是只保留 happy path。

重点测试：

- 过滤 `标记`、`时间戳记` 等元数据列
- `Multiple Choices` 识别为多选题
- 自由文本建议题识别为开放题
- `other/其他说明` 配对正确
- 生成的 schema 包含分类与题型
- 报告只接受存在的 `Analysis Run`

建议同时保留：

- 小型 synthetic fixture
- 至少一份贴近真实结构的 fixture

## 8. 成功标准

这一轮完成后，至少应达到：

- 真实验收样本中的多选题不再被识别成单选题
- 明显开放题不再被识别成单选题
- 系统列不再混入主问题列表
- `Analysis Run` 具有清晰的持久化语义
- 后续报告链路继续保持可跑通

## 9. 后续衔接

本轮完成后，最自然的下一阶段是：

1. 扩展确定性统计能力，让 schema 真正驱动多选/量表/开放题分析
2. 再把知识库增强分析和报告内容质量做上去

也就是说，顺序应是：

**先把数据理解层做对，再把分析和报告做深。**
